    Priority Queue — Multi-Lane Architecture

    4 Internal FIFO Queues

    Our C implementation maintains four internal queues: Critical, High, Medium, and Low. When an allocation is requested, the system serves the highest non-empty priority lane first. Within the same priority lane, earlier arrivals are strictly served first (FIFO).

      Key Viva Questions & Detailed Answers

      Exam Preparation
      Q1. Why is a Priority Queue used instead of a simple FIFO Queue for disaster relief?
      In a disaster scenario, requests arrive with drastically different levels of life-threatening severity. A simple FIFO queue would force a critical blood/medicine request to wait behind a non-urgent blanket request simply because the blanket request arrived two minutes earlier. A Priority Queue ensures that critical and life-saving demands are always served first, regardless of arrival order.
      Q2. How does your Priority Queue break ties between requests with the same priority?
      Our C implementation uses four separate FIFO queues internally (one for each priority level). When two requests have the exact same priority (e.g. both are "Critical"), they enter the same lane queue. Because each lane is a true FIFO queue with front and rear pointers, requests within that lane leave in the exact order they entered. Thus, priority takes precedence, and arrival order breaks ties.
      Q3. Why is a Stack chosen for the Undo Last Allocation feature?
      A Stack operates on the Last-In, First-Out (LIFO) principle. An undo operation must always reverse the most recently executed action first. The top of the stack naturally holds the latest allocation, allowing O(1) retrieval and reversal of warehouse inventory, request status, and linked list records.
      Q4. How does the WebAssembly bridge communicate between C and JavaScript?
      The C source files are compiled using Emscripten with WebAssembly flags into a binary relief_q.wasm and glue script relief_q.js. The frontend passes inputs across the memory boundary via exported C functions (rq_allocate_next, rq_submit_request, etc.), and the C engine serializes its state into JSON stored in a memory buffer. JavaScript parses this output and renders the UI. The C engine remains 100% authoritative for the simulation state.
